# MDQ Extended Markdown Specification

**Status:** 0.1.0-draft (proposed, not an implemented standard)  
**Normative base:** CommonMark, with the GFM profile for tables, strikethrough, task lists and autolinks.  
**Encoding:** UTF-8; input MUST reject malformed UTF-8.  
**Scope:** Authoring, resolution, evaluation and Markdown export. The binary `.mdq` package is specified separately.

## 1. Principles and conformance

The terms MUST, MUST NOT, SHOULD and MAY are normative. A plain `.md` file without MDQ directives MUST remain valid input. MDQ processors MUST preserve ordinary CommonMark semantics. MDQ is a preprocessor and document model, not a replacement Markdown renderer. `mdq build` MUST produce standard Markdown without unresolved MDQ directives. A conforming implementation MUST publish supported feature profiles; unsupported required features MUST fail rather than silently disappear.

Profiles: **core** (imports, references, variables, metadata, identifiers, conditional and repeated content), **rich** (GFM, footnotes, highlights, callouts, maths display, Mermaid, citations, containers, columns, details, TOC), **calc** (safe deterministic expressions), **package** (archive and encrypted resources). Rich features are included in the MDQ specification but may require a rendering adapter; their portable export MUST be specified.

## 2. Lexical rules

MDQ directives MUST NOT be interpreted inside fenced/indented code, inline code, raw HTML blocks, or escaped sequences. A backslash immediately before an MDQ opening delimiter escapes that delimiter (e.g. `\\{{x}}` renders literal `{{x}}`). Implementations MUST parse Markdown structure before expanding inline directives; global regular-expression replacement is not conforming. Paths use forward slashes, are relative to the referencing file unless declared otherwise, and are case-sensitive within the MDQ virtual filesystem. A path MUST NOT escape the authorised root after canonicalisation, including through symlinks. URLs and remote imports are disabled by default.

## 3. Composition and links

- `![[path.md]]` transcludes the full source body, excluding YAML frontmatter.
- `![[path.md#Heading]]` transcludes a heading and its section up to the next heading of equal or higher level.
- `![[path.md#^block-id]]` transcludes a uniquely identified block.
- `[[path.md]]`, `[[path.md#Heading]]`, `[[path.md#^block-id]]` produce links, not embedded content.
- `[[path.md#Heading|Label]]` sets the visible label.
- `^block-id` at the end of a paragraph identifies that paragraph; the identifier marker is omitted from compiled output. IDs match `[A-Za-z][A-Za-z0-9_-]*` and MUST be unique per source document.

References MUST resolve to explicit relative paths; filename-only global searches are not performed. Heading matching uses Unicode NFC and exact visible heading text (case-sensitive) in draft 0.1. Duplicate matching headings resolve to the FIRST matching heading in source order. To target a later duplicate, attach and reference an explicit block ID. This rule applies independently in each source document. For a transcluded section, heading levels are preserved. Implementations MUST detect import cycles, including section imports. A link generated by a reference MUST be rewritten to point to the compiled target when available; otherwise it MUST remain a valid relative Markdown link to a copied dependency or fail with `MDQ_UNRESOLVED_REFERENCE`. Duplicate heading anchors in a combined output MUST be disambiguated deterministically using §3.1. Source-qualified references retain the identity of their original document even when imported multiple times.


### 3.1 Heading identity, anchors and exported links (normative)

A heading reference `[[path.md#Heading]]` matches the heading's rendered plain-text content after Markdown inline markup is stripped, HTML entities decoded and Unicode NFC normalisation applied. Matching is case-sensitive and whitespace is collapsed to a single ASCII space and trimmed. The FIRST matching heading in the referenced source file wins; later duplicates require an explicit `^block-id`. Matching never searches imported/rendered copies or other files. A source-qualified target is the tuple (canonical source path, heading ordinal or explicit block ID), not an output slug.

For portable generated anchors, normalise the heading's visible text to Unicode NFC; apply Unicode default case folding; retain Unicode letters, numbers, combining marks, hyphen and underscore; replace each run of other characters (including whitespace and punctuation) with one hyphen; trim leading/trailing hyphens. Empty results use `section`. The first occurrence of a base slug is `base`, the next `base-2`, then `base-3`, etc. Slug collision tracking occurs within each output file. Percent-encode non-ASCII characters when serialising anchor URLs, but preserve Unicode in the actual HTML `id`. A user-authored block ID has priority as its own anchor and MUST NOT collide with another generated ID; generated collisions MUST be deterministically renamed. Exporters MAY use a renderer-specific algorithm only in a declared non-portable profile; the portable profile MUST use this algorithm.

Imports preserve the source identity of every node. Repeatedly importing a file does not change how `[[that-file.md#Heading]]` resolves; the compiler maps the source target to its first rendered occurrence in the relevant output, unless the exporter has an explicit occurrence selection policy. If a source target is absent from the output, the exporter MUST emit a working link to a separately exported file or fail with `MDQ_UNRESOLVED_REFERENCE`; it MUST NOT generate a broken anchor.

Ordinary relative Markdown links and image destinations inside imported content resolve against the ORIGINAL containing file, not the importer. For example, importing `chapters/intro.md` containing `![Diagram](images/flow.png)` into `index.md` requires a destination resolving to `chapters/images/flow.png` when emitted alongside the original tree. When exporting to a different directory or a single-file format, the exporter MUST rewrite destinations or copy/inline assets to keep links valid. Absolute external URLs are not rebased. For HTML export, Markdown links MUST point to generated HTML paths and HTML anchors, not raw `.md` targets, when those targets are included in the export.

### 3.2 Normative versus illustrative material

Sections explicitly marked **normative**, and all unqualified MUST/MUST NOT/SHOULD/MAY requirements, define conformance. Code examples are **illustrative** unless expressly labelled as test vectors. Where an example conflicts with a normative rule, the normative rule prevails and the example MUST be corrected. Conformance fixtures are normative only where their expected outputs are explicitly declared and versioned.

## 4. Variables

`{{namespace.key}}` interpolates a scalar (string, boolean, number, null). Dotted names use ASCII identifier segments. Missing values raise `MDQ_UNDEFINED_VARIABLE`; no implicit environment variables, filesystem reads or expression evaluation are permitted. Values are converted to text using: strings unchanged, booleans `true`/`false`, null empty, numbers decimal canonical form. Objects and arrays MUST NOT interpolate without an explicit renderer. Expansion in inline Markdown text MUST escape Markdown metacharacters by default; trusted raw insertion requires a separate opt-in capability, not supported by core 0.1. Variable sources MAY be JSON or YAML mappings declared in metadata. Variables defined by `calc` are available as `calc.name` after evaluation.

## 5. Metadata and cascade

Documents MAY start with YAML frontmatter enclosed by `---` lines; it MUST be a mapping. A sidecar named `<stem>.meta.yaml` MAY accompany a document. A package manifest is mandatory only for the package profile. The metadata schema is shared. Precedence for ordinary presentation/data keys, highest first: explicit invocation overrides > document sidecar > document frontmatter > nearest directory metadata (`.mdq.yaml`, moving outward) > project `.mdq.yaml` > defaults. Nested mappings merge recursively; scalars and arrays replace lower-precedence values in full. `null` explicitly clears a non-required value. Duplicate YAML mapping keys MUST fail. Untrusted metadata cannot grant permissions: effective capabilities are the intersection of trusted host policy and requested capabilities; mandatory security restrictions compose by the most restrictive rule.

Example:

```yaml
mdq: '0.1'
variables:
  project: ./data/project.yaml
features: [core, rich, calc]
rules:
  remote_imports: false
  undefined_variables: error
```

Frontmatter fields are available under `document.*`, while imported variable mappings use their declared namespace. Conflicting reserved namespaces MUST fail. Frontmatter, sidecars, directory metadata and project metadata accept the SAME schema; they are alternative locations, not paired declarations. Source definitions and their uses MAY be colocated. See `sources-and-permissions.md` for source declarations and security precedence.

## 6. Conditional and repeated content

Containers use lines of three or more colons, beginning at column zero; matching close fences use the same number of colons. Nested containers MUST use a longer delimiter than their parent. The following are core:

```text
:::if {var="flags.public" equals="true"}
Public text.
:::
:::for {each="items" as="item"}
- {{item}}
:::
```

`if` compares a scalar variable to a quoted literal (string comparison in draft 0.1); `for` iterates a declared array in source order, binding the loop variable in lexical scope. No general-purpose expression language is implied. `else`, nested expressions, and filters are reserved for a future version. Conditions are evaluated before transclusion of their bodies, so excluded branches MUST NOT read imports or decrypt resources. Loops have host-configured iteration limits.

## 7. Rich authoring features

- **GFM:** tables, task lists, strikethrough and autolinks follow the GFM specification.
- **Quotes:** CommonMark `>` blockquotes.
- **Footnotes:** `[^id]` and `[^id]: explanation`; identifiers MUST be scoped and renamed deterministically on transclusion.
- **Highlights:** `==text==`; plain Markdown export removes delimiters and preserves text.
- **Callouts:** `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]`, `> [!CAUTION]`; plain Markdown fallback is a blockquote with a bold label.
- **Maths display:** `$...$` inline and `$$` fenced display maths (LaTeX-style notation); processors MUST NOT execute LaTeX commands or shell escapes. Plain Markdown export MAY retain the notation if the chosen target profile supports it; strict CommonMark export MUST use a code/text fallback.
- **Mermaid:** fenced `mermaid` code block. A renderer MAY generate a diagram, but MUST treat source as untrusted; plain Markdown export retains the fenced source unless a separately requested static image export exists.
- **Citations:** `[@key]` and `[@key, p. 12]`, resolved from declared CSL JSON or BibTeX resources. Missing keys fail; style and bibliography formatting are delegated to a declared citation profile. Portable fallback MUST preserve a readable citation label and bibliography.
- **TOC:** `[[toc]]` expands into links to resolved headings, including imported headings.
- **Details:** `:::details {title="Details"}` contains Markdown; plain Markdown fallback is a heading plus contents.
- **Columns:** `:::columns` with nested `::::column` blocks; plain Markdown export linearises columns in source order. Columns are layout, not tabular data.
- **Generic fenced containers:** `:::vendor.name {key="value"}`; unknown required handlers fail, optional ones MAY preserve body as Markdown with a warning. Extension attributes are declarative; no implicit code execution.

## 8. Calculations (normative simple language)

MDQ calculations are intentionally small: **assignment, decimal arithmetic, percentages, unit quantities, conversion and references to already resolved variables**. No network requests or general function calls occur in `calc`. The parser MUST NOT evaluate Python, Rust, JavaScript or arbitrary user code. An implementation grammar MAY be more formal internally, but MUST NOT expose extra expression constructs as core MDQ.

### 8.1 Authoring

A fenced `calc` block contains one assignment per non-empty line; full-line `#` comments are permitted. Identifiers match `[A-Za-z][A-Za-z0-9_]*`; an assignment may refer to earlier assignments in that block and to scalar variables from effective metadata. Assignments MUST be unique within the block. Supported operators are unary `+`/`-`, binary `+ - * /`, parentheses and a postfix percentage (`21%` means `0.21`). Arithmetic follows conventional precedence. No exponentiation, conditions, indexing, loops or arbitrary calls. Decimal arithmetic MUST use at least 28 significant digits with ROUND_HALF_EVEN by default; divide-by-zero is an error.

```calc
price = 120 EUR
quantity = 4
subtotal = price * quantity
tax = subtotal * 21%
total = subtotal + tax
```

`{{calc.total}}` accesses the computed result. Every block has its own local assignment scope. To avoid ambiguity, multiple blocks in the same output MUST NOT export the same `calc.name` unless the compiler is given a disambiguating namespace; the default is `MDQ_CALC_ERROR`. Assignments shadow metadata names **within their block only**; they do not mutate metadata. Forward references to later assignments fail.

### 8.2 Unit quantities and conversion

A quantity is a decimal followed by a catalogue unit token, e.g. `12 miles`, `150 lb`, `72 degF`. Conversion is written `value to unit`, e.g. `distance_km = distance to km`. `to` binds after arithmetic; parentheses disambiguate when needed. The versioned MDQ unit catalogue in `calculation-units.md` is normative for supported categories and canonical symbols; the exact expression and dimensional semantics are defined in §8.5–8.9. Libraries MUST reject unknown units, incompatible dimensions and illegal operations on absolute affine temperatures. Bare `C` and `F` are ambiguous and MUST NOT mean temperature; use `degC` and `degF`. Implementations MUST expose the catalogue version used.

```calc
distance = 12 miles
distance_km = distance to km
temperature = 72 degF
temperature_c = temperature to degC
```

### 8.3 Currency and external observations

Currencies are typed quantities using ISO 4217 codes. `profit_eur = profit to EUR` is permitted **only if** an appropriate exchange-rate observation has already been supplied to the library by the host. The library MUST NOT fetch it. An unavailable rate produces `MDQ_SOURCE_UNRESOLVED`, not an implicit live lookup. The reader determines date, market conventions, freshness and provider, and MUST supply provenance and any conversion observations as resolved input. Stock prices are likewise ordinary typed input variables, not `stock()` calls in `calc`.

```calc
shares = 10
value_usd = apple_price * shares
value_eur = value_usd to EUR
```

`apple_price` is a metadata-declared or host-injected typed variable. No `stock()`, `fx()` or HTTP function is part of the `calc` grammar. External source declarations are defined in `sources-and-permissions.md`.

### 8.4 Export and errors

Core evaluation MUST be deterministic for identical typed inputs, unit catalogue and configuration. `calc` blocks MUST NOT read files, access the clock or make network calls. Errors include unknown identifiers, unsupported operations, duplicate assignments, incompatible units and division by zero (`MDQ_CALC_ERROR`); unresolved external inputs use `MDQ_SOURCE_UNRESOLVED`. Portable export substitutes references to results and, unless explicitly requested, omits calculation source. The `calc` grammar and unit catalogue are identical in `.md` and `.mdq`; package-only trusted extensions MAY add units but MUST NOT silently alter existing unit definitions or introduce arbitrary code execution.


### 8.5 Complete core expression grammar (normative)

The grammar below defines the entire `calc` 0.1 expression surface. Whitespace is allowed between tokens; newline terminates a statement. A `#` starts a comment ONLY when it is the first non-whitespace character on a line. No inline comments, semicolons, strings, function calls, implicit multiplication, exponentiation, booleans, comparisons or assignment expressions are supported.

```ebnf
block       = { blank | comment | assignment } ;
assignment  = identifier, ws, "=", ws, expression, newline ;
expression  = conversion ;
conversion  = sum, [ ws1, "to", ws1, unit ] ;
sum         = product, { ws, ("+" | "-"), ws, product } ;
product     = unary, { ws, ("*" | "/"), ws, unary } ;
unary       = { "+" | "-" }, postfix ;
postfix     = atom, [ "%" ] ;
atom        = number, [ ws1, unit ] | identifier | "(", ws, expression, ws, ")" ;
identifier  = ASCII_LETTER, { ASCII_LETTER | DIGIT | "_" } ;
number      = DIGIT, { DIGIT }, [ ".", DIGIT, { DIGIT } ]
            | ".", DIGIT, { DIGIT } ;
unit        = a single longest-match token in the active unit catalogue
            | an ISO 4217 currency code ;
ws          = { " " | TAB } ;
ws1         = (" " | TAB), ws ;
newline     = LF | CRLF | end-of-block ;
```

A `calc` block MUST have zero or more assignments; an empty block is valid. Numeric literals are base-10 finite decimals; scientific notation, `NaN`, infinities and thousands separators are not supported in 0.1. Units containing `/` (such as `km/h`) are recognised by longest match when adjacent to a number or following `to`; this tokenisation takes precedence over division only at those unit positions. `12 km/h` is a quantity, while `12 / h` is invalid unless `h` is a defined variable. Parenthesised conversions such as `(distance to km) / 2` are valid. Chained conversions (`x to km to miles`) are invalid; use parentheses or a second assignment.

`%` applies only to a numeric or parenthesised dimensionless atom, never a dimensioned quantity: `21%` and `(5 + 5)%` are valid; `2 kg%` is invalid. Percentage has higher precedence than unary signs; multiplication/division bind more tightly than addition/subtraction; conversion `to` binds more weakly than arithmetic. Operators at the same precedence associate left-to-right. `-2^2`, `2(3)` and `1 // 2` are invalid.

### 8.6 Names, scopes, evaluation and output (normative)

Identifiers are ASCII and case-sensitive. Each block has its own scope. A reference resolves to the latest earlier assignment in that block, then to an effective typed metadata/host variable; if neither exists, it is an error. A later local assignment cannot be referenced before its line. Duplicate assignment names within a block are invalid. Metadata values are immutable; a local assignment may shadow one for the remainder of its block. Other `calc` blocks do not share local scope. Exported results are named `calc.<identifier>` and collisions across blocks are errors unless the trusted invocation assigns explicit distinct block namespaces. Metadata variables can be referenced by their simple identifier in `calc`; dotted metadata paths and `{{...}}` interpolation are not expression syntax. A host MUST provide any required values as named typed inputs before evaluation. Result interpolation is only available after evaluation, and interpolation before definition is an error.

`calc` output types are `decimal`, `quantity(decimal, dimension, unit)`, or `money(decimal, currency)`. The engine MUST preserve a result's type and unit; formatting for display is a separate rendering concern. For `{{calc.name}}`, the portable default renders a dimensionless decimal canonically and a quantity as `<decimal> <unit>`, with no thousands separators. Canonical decimals remove unnecessary trailing fractional zeroes and use `0` for negative zero. A result with an unresolved source MUST fail, not render an empty value.

### 8.7 Arithmetic and dimensional rules (normative)

Addition/subtraction require matching dimensions. Compatible quantities are converted to the LEFT operand's unit before calculation. A bare number is dimensionless; adding it to a dimensioned quantity is invalid. Multiplying or dividing quantities combines/subtracts dimension exponents; dimensionless multiplication/division preserves the other operand's unit. The core 0.1 grammar supports products and ratios of quantities internally, but conversion `to` requires a catalogue target with the SAME resulting dimension; it MUST reject conversions to an unrelated dimension. Division by zero is always an error. Results MUST be computed with at least 28 decimal significant digits and round-half-even when precision is exhausted; implementations MUST expose the configured precision, and fixed-input conformance fixtures MUST specify it.

Absolute temperatures (`degC`, `degF`, `K`) use affine conversion and MUST NOT be multiplied or divided, added together, or used as a factor in a compound unit. Subtracting two absolute temperatures produces a temperature DIFFERENCE in kelvin increments (display unit `deltaK`); adding or subtracting a temperature difference to/from an absolute temperature is reserved for a later revision and MUST fail in 0.1. Temperature differences MAY be multiplied by dimensionless numbers. Celsius/Fahrenheit absolute conversion uses the exact formulae in the unit catalogue. Percentages are dimensionless factors. Money multiplied/divided by a dimensionless scalar retains its currency; money-to-money division is allowed only for the same currency and yields a dimensionless ratio; money plus/minus money requires the same currency (explicit `to` for conversion). Multiplying two money amounts or money by a physical quantity is invalid in 0.1; `price * shares` is valid when shares is dimensionless.

### 8.8 Currency observation selection (normative)

`amount to EUR` for money requires a host-supplied conversion observation. An observation has `from`, `to`, positive finite decimal `rate`, `observed_at` (ISO 8601 timestamp), `provider` and optional `market`. The trusted invocation MUST specify a valuation timestamp or an explicit observation identifier for each currency conversion. Only observations with matching currency pair, required market (if set) and an exact requested observation identifier OR the latest `observed_at` not later than the valuation timestamp are eligible. When multiple eligible observations have the same timestamp, the host MUST specify an observation identifier; the engine MUST NOT choose arbitrarily. No automatic reverse-rate inversion, triangulation, fallback to stale rates or current-clock lookup occurs in 0.1. Missing or ambiguous observations produce `MDQ_SOURCE_UNRESOLVED`. A supplied rate is applied as `amount * rate`, retaining the target currency. The engine MUST NOT retrieve observations itself.

### 8.9 Required diagnostics and test vectors (normative)

Invalid syntax, duplicate or forward identifiers, unsupported operators, invalid percentages, incompatible dimensions, absolute-temperature misuse, unknown units and division by zero produce `MDQ_CALC_ERROR` with the block and line location. Unresolved external values or currency observations produce `MDQ_SOURCE_UNRESOLVED`. A conforming implementation MUST cover the following test vectors at 28-digit precision:

| Expression / statements | Expected result |
| --- | --- |
| `x = 10` | `10` |
| `x = 2 + 3 * 4` | `14` |
| `x = (2 + 3) * 4` | `20` |
| `x = 120 * 21%` | `25.2` |
| `x = 12 miles to km` | `19.312128 km` |
| `x = 32 degF to degC` | `0 degC` |
| `x = 10 / 0` | `MDQ_CALC_ERROR` |
| `x = 2 kg + 3 m` | `MDQ_CALC_ERROR` |
| `x = 1 + 2; y = 3` | `MDQ_CALC_ERROR` |
| `x = stock("AAPL")` | `MDQ_CALC_ERROR` |

The unit catalogue and source specifications remain separately normative. A full claim of unit-catalogue conformance is contingent on publishing its complete canonical table.

## 9. Processing order

1. Decode UTF-8, parse CommonMark and frontmatter; load and validate trusted metadata.
2. Establish effective capabilities and resolve variable sources within allowed roots.
3. Parse MDQ syntax and build a dependency graph; reject cycles and ambiguous identifiers.
4. Evaluate conditionals/loops, then resolve included branches and transclusions with scoped metadata.
5. Evaluate `calc` blocks and interpolate variables; resolve citations, footnotes, references and TOC.
6. Apply rich-format fallbacks for selected export profile and validate no unresolved required constructs remain.
7. Emit UTF-8 Markdown and optional provenance/dependency diagnostics.

A conforming implementation MUST make the result deterministic for fixed inputs and configuration. The core processor has no network or clock access. Optional source resolvers are invoked by the trusted host under the separate source and permissions specification; fixed-input builds MUST remain reproducible.

## 10. Security defaults

No remote imports, executable plugins, arbitrary scripts or implicit decryption. Imports are confined to an authorised root. Processors MUST bound recursion depth, total expanded bytes, loop iterations and archive expansion. Raw HTML and links MUST be sanitised by HTML renderers according to their host threat model; Markdown preprocessing alone is not an HTML sandbox. Sensitive data MUST NOT be exported in plaintext unless the trusted host explicitly authorises it. The `.mdq` package profile will define `age` encrypted members and whole-package encryption separately; encrypted resources are not core `.md` syntax.

## 11. Diagnostics

Minimum stable diagnostic codes: `MDQ_UNDEFINED_VARIABLE`, `MDQ_MISSING_IMPORT`, `MDQ_IMPORT_CYCLE`, `MDQ_AMBIGUOUS_REFERENCE`, `MDQ_UNRESOLVED_REFERENCE`, `MDQ_DUPLICATE_ID`, `MDQ_METADATA_ERROR`, `MDQ_INVALID_SYNTAX`, `MDQ_UNSUPPORTED_FEATURE`, `MDQ_SECURITY_DENIED`, `MDQ_CALC_ERROR`, `MDQ_RESOURCE_LIMIT`, `MDQ_SOURCE_UNRESOLVED`, `MDQ_SOURCE_INVALID`, `MDQ_SOURCE_FETCH_FAILED`, `MDQ_SOURCE_TYPE_ERROR`. Errors MUST include source path and location where available.

## 12. Interoperability items for future revisions

- Formal grammar for all MDQ delimiters and interaction with CommonMark link parsing.
- Additional export-target-specific anchor mapping beyond the portable algorithm in §3.1.
- Citation formatting baseline and bibliography placement.
- Escaping of interpolated values in link destinations versus ordinary prose.
- Whether YAML frontmatter `---` conflicts with an initial thematic break in ambiguous documents.
- Explicit resource-limit defaults and richer feature capability negotiation.

The above items are explicitly non-normative future refinements. This document is a 0.1 draft and does not claim independent interoperability certification.
